- **Corrección de seguridad en `run_command`:** originalmente usaba `shell=True` con el string de comando tal cual. Se cambió a tokenizar con `shlex` + `shell=False`, cerrando el vector de inyección de comandos (`;`, `&&`, `|` dejan de ser operadores de shell y se pasan como argv literal — hay un test de regresión que lo confirma). **Costo funcional real, no una elección mía:** se pierde soporte para pipes, redirects (`>`/`<`), expansión de variables (`%VAR%`).
- **Aislamiento Windows-específico en `ProcessAgent`:** `list_processes`/`get_process_info`/la verificación de existencia de `kill_process` quedaron detrás de `_list_processes_windows()`/`_get_process_info_windows()`, con un único punto de detección de SO (`_require_windows()`, vía `platform.system()`). Los handlers públicos no saben que son Windows-específicos. Linux/Mac levantan `NotImplementedError` desde ese único punto — no implementados todavía, ver `execute()` que ahora también atrapa `NotImplementedError` y lo retorna como `ActionResult(FAILED)`, consistente con "nunca propagar excepciones".
- **Corrección del tokenizador de `run_command` (`shlex.split(..., posix=False)` + limpieza manual de comillas, en `_split_command()`):** `shlex.split()` en modo POSIX (el default) trata `\` como carácter de escape, corrompiendo rutas Windows **sin comillas** (`C:\Windows\System32\app.exe` → `C:WindowsSystem32app.exe`, verificado empíricamente). `posix=False` preserva las barras invertidas, pero como efecto secundario deja las comillas de agrupación como caracteres literales en el token — así que `_split_command()` las remueve a mano después de tokenizar. Con esto, tanto rutas sin comillas como argumentos entre comillas (`-c "código"`) funcionan correctamente; hay test para ambos casos.
- **Decisión sobre comandos internos de cmd.exe — cerrada, no queda pendiente:** `dir`, `cd`, `echo`, `type`, `copy`, `del`, `set`, `cls`, etc. no tienen `.exe` propio en Windows (solo existen dentro de un shell), así que `run_command(command="dir")` falla con `ActionResult(FAILED)` — y **se deja así a propósito**, no se agrega un prefijo automático `["cmd", "/c", ...]` que reintroduzca superficie de shell. Razón: esa funcionalidad ya existe donde corresponde — listar/crear/borrar archivos es `FileSystemAgent` (`list_directory`, `delete_file`, etc.), y cambiar de directorio para un comando es el parámetro `cwd` que `run_command`/`run_script` ya aceptan. `ProcessAgent` es deliberadamente solo para ejecutables reales, no para reimplementar un shell.

### Sesión nocturna autónoma — GitAgent (tercer IAgent concreto)

- `src/aries/agents/git/agent.py`: **tercer `IAgent` concreto.** `GitAgent` ejecuta operaciones Git invocando el binario `git` vía `subprocess`, siempre `shell=False` con argv explícito (ninguna capacidad interpola texto libre en un comando de shell — no hay un `run_git_command(command: str)` genérico tipo `ProcessAgent.run_command`). Capacidades: `status`, `add` (archivos específicos o todo vía `git add -A`), `commit`, `push`, `pull`, `log` (últimos N commits, parseados con un separador `\x1f` para evitar ambigüedad con mensajes que contengan el delimitador obvio), `diff` (working tree o `--staged`), `branch_list`, `branch_create` (con `checkout` opcional), `branch_checkout`, `reset` (`mode="soft"|"hard"`, default `"soft"`). `requires_confirmation()` usa el mismo patrón de extensión ya documentado en `docs/contracts/IAgent.md` (kwargs opcionales además de `action`): `True` para `push(force=True)` y `reset(mode="hard")`, que son exactamente los dos casos que la tarea pidió explícitamente — con el set de capacidades actual no hay otra operación que reescriba historia (no hay `rebase`/`commit --amend`/`filter-branch`).
- **Diferencia deliberada de filosofía vs. `ProcessAgent`:** en `GitAgent`, `ActionResult.status` refleja el resultado semántico real de la operación de Git (`exit_code != 0` → `FAILED`), no solo si el proceso pudo arrancar. Es lo opuesto a `ProcessAgent.run_command`/`run_script`, donde `SUCCESS` significa "el shell/intérprete corrió" sin importar el `exit_code` del programa. Tiene sentido acá porque cada capacidad de `GitAgent` es una operación con significado propio (`commit` "tuvo éxito" o no), a diferencia de `run_command` que ejecuta cualquier cosa.
- **Sin capa de aislamiento de SO** (a diferencia de `ProcessAgent`/`_require_windows()`): `git` es el mismo binario con el mismo comportamiento en Windows/Linux/Mac, no hay ninguna llamada SO-específica que aislar. Documentado explícitamente en el docstring del módulo para que quede claro que es una omisión deliberada, no un olvido.
- **Hallazgo empírico no obvio, verificado antes de escribir el código (no asumido):** Git no es consistente sobre a qué stream de salida manda sus mensajes informativos — `checkout`/`push` escriben su resumen a **stderr** incluso en éxito (exit 0); `reset --hard`/`pull` usan **stdout**. `execute()` arma `output` con fallback `stdout or stderr` para cubrir ambos casos. También: en Windows, `subprocess.run(cwd=<algo>)` levanta `NotADirectoryError` tanto si el path no existe como si existe pero es un archivo — nunca `FileNotFoundError` para esos casos (sí para cuando no se encuentra el binario `git` en sí). El mensaje de error de `repo_path` se redactó para cubrir ambos casos.
- **Alcance de `reset` deliberadamente acotado a `soft`/`hard`**, sin `mixed` — la tarea solo mencionó esos dos modos explícitamente; no se amplió sin que se pidiera. Default `mode="soft"` (el menos destructivo de los dos soportados) por ser la sesión nocturna sin supervisión: ante ambigüedad, la opción más conservadora.

**Decisión de arquitectura resuelta vía `AskUserQuestion` antes de escribir código** (fork real, no ambigüedad menor): ¿`Kernel.run()` debía levantar el servidor FastAPI de `api.py` él mismo (Kernel como proceso raíz), o quedarse como bucle de fondo mientras uvicorn sirve `api.py` por separado? Se eligió **la segunda opción** — razones: (1) consistente con la decisión 7 ya aprobada en `Planner.spec.md` ("el front door es `POST /message`, no el Kernel", tomada explícitamente la tarea anterior); (2) la primera opción hubiera exigido reestructurar el patrón de singletons a nivel de módulo de `api.py` (de donde dependen los 342 tests existentes) en una fábrica inyectable, un refactor real y riesgoso solo para que el Kernel "posea" el servidor; (3) más testeable — el ciclo de vida del Kernel se prueba sin necesitar HTTP, y viceversa.

### `AgentManager` unificado: un plugin cargado por Kernel queda dispatchable de verdad vía `POST /message`

La tarea anterior cerró *cómo* se invoca un plugin (`execute()` + `PluginAgentAdapter`) pero dejó documentado que el `AgentManager` con plugins vivía aislado dentro del Kernel, sin relación con el que usaba el Planner en `api.py`. Esta tarea unifica los dos en uno solo.

### `kernel.run()` conectado al ciclo de vida de la API — housekeeping de fondo real, no solo `initialize()`/`shutdown()`

La tarea anterior dejó `_kernel` cableado a `api.py` pero solo a través de `initialize()`/`shutdown()` — el bucle de housekeeping (`run()`) seguía sin invocarlo nadie por defecto, un gap explícitamente documentado ahí. Esta tarea lo cierra.

- **`src/aries/api.py` — `startup_event()`:** después de `await _kernel.initialize()`, lanza `_kernel_run_task = asyncio.create_task(_kernel.run())` — **sin `await`**, a propósito: `run()` es un bucle de vida larga que no vuelve hasta que `shutdown()` lo señala, así que esperarlo ahí colgaría el arranque de la app para siempre. La referencia a la task se guarda en `_kernel_run_task`, una nueva instancia a nivel de módulo (mismo patrón de singleton que `_kernel`/`_memory`/etc.).
- **`shutdown_event()`:** primero `await _kernel.shutdown()` (ya señala el `asyncio.Event` interno que hace salir a `run()` de su bucle, ver `core/kernel.py`), y **después** `await _kernel_run_task` — sin cancelar. `run()` ya estaba diseñado (desde la tarea que lo conectó a `Kernel.shutdown()` originalmente) para salir solo apenas se le señala, así que cancelarlo a la fuerza sería innecesario y arriesgaría cortarlo a mitad de un ciclo de `memory.clear_expired()`. El `await` confirma que terminó limpio antes de que el proceso de shutdown de la app continúe.
- **No se tocó `core/kernel.py`** — `run()`/`shutdown()` ya estaban diseñados exactamente para este patrón (señal + espera, sin cancelación) desde la tarea que los conectó por primera vez; esta tarea solo fue cablear ambos lados desde `api.py`.
- **Test de integración real nuevo, en `tests/integration/test_api_message.py::TestKernelRunBackgroundTaskViaAPI`:** intervalo de housekeeping bajado a `0.05` solo para el test (`api.settings.kernel_housekeeping_interval_seconds`, restaurado en `finally`); se suscribe un handler real a `api._event_bus` (el bus real y compartido, no uno nuevo) antes de levantar la app; `with TestClient(app) as client:` dispara el ciclo de vida real; confirma que `KernelStartingEvent` se publicó exactamente una vez, que un `MemoryItem` ya vencido en `api._memory` (la Memory real y compartida) desaparece solo tras un par de ciclos de housekeeping reales, y que al salir del `with` la task guardada en `api._kernel_run_task` terminó (`done()`), sin haber sido cancelada (`not cancelled()`) y sin excepción (`exception() is None`).
- **Verificado empíricamente antes de escribir el test, no asumido:** `TestClient` corre el ciclo de vida de la app (incluida la task de `run()`) en un hilo/loop de asyncio separado del loop del test — se confirmó con un repro mínimo que un handler suscripto en el loop del test sí recibe eventos publicados desde ese otro loop, y que operaciones sobre el mismo `InMemoryStore` compartido (con su `asyncio.Lock` interno) funcionan correctamente entre ambos loops en este stack (Python 3.12, Starlette 0.50) sin condición de carrera observable, dado que no hay contención real entre ambos accesos.

### Persistencia real de Memory: `SQLiteMemoryStore`

Instrucción explícita de la tarea: nada de `voice/`, `Planner`, `Brain`, `Kernel` ni ningún `IAgent` — solo persistencia de Memory. Ningún archivo de esas áreas se tocó.

  - Tabla `memory_items` con una columna por campo de `MemoryItem` (`metadata` como columna `JSON`, `created_at`/`updated_at`/`expires_at` como `DateTime` — SQLAlchemy hace el round-trip `datetime`↔texto automáticamente).

Verificado con un test dedicado que confirma que la búsqueda es case-sensitive igual que `InMemoryStore`.
